### 실제 남은 작업 — 품질 기준
1. **먼저 기존 소스를 시각적으로 확인**하라. 물고기 PNG는 기존의 한국 아동용 귀여운 낚시 게임 감성을 최대한 유지한다. 기존 캐릭터, 구도, 색감, 실루엣, 방향을 레퍼런스로 써라. 새 그림의 디자인이 다른 어종과 튀거나 배경이 기존 세계관에서 벗어나지 않게 한다.
2. `fish_sunfish.png`, `fish_tuna.png`는 현재 **256×256 원본**이며 포획 화면에서 실제 피사체 픽셀 밀도가 부족하다. 고해상도 원본을 획득하거나 연결된 **실제 이미지 생성/리드로잉 도구**가 있다면 **새 디테일을 포함하는 768~1024px 수준의 투명 PNG**로 개선하라. 원본의 단순 bicubic/Lanczos 2~4배 확대, 미리보기 샤프닝, 무의미한 빈 캔버스 확대만으로 '해상도 해결'이라고 판단하지 말라.
3. 다음 후보: `fish_gwangeo.png`, `fish_striped_jewfish.png` (기존 256px)와 `docs/image-qa.md`에 표기된 대상. 다만 실질 화질 개선이 확인되지 않으면 **기존 PNG를 유지**하라.
4. 지역 배경 4개(`bg_freshwater.png`, `bg_coast.png`, `bg_sea.png`, `bg_treasure_island.png`)는 현재 원본이 각각 640×640 JPEG(앞의 3개) / 360×640 PNG(보물섬)이다. 새로 작업할 수 있다면 **720×1280 이상, 9:16의 실제 세로 구도**를 마련하되 낚시터 상단 지평선·중앙 수면·하단 플레이어 공간을 보존하라. 원본을 재생성할 방법이 없거나 품질을 객관적으로 개선하지 못하면 기존 파일과 코드의 cover 방식을 유지하라. 파일 확장자뿐 아니라 파일 내부 포맷도 일치시켜라.
5. 달빛 잉어/폭풍 참치 전용 PNG는 있으면 좋지만 **선택 사항**이다. 현재 기존 잉어/참치 텍스처 공유 + Phaser 이펙트가 이미 동작한다. 신규 PNG를 만들었을 때에만 로더, 참조, 기본 틴트 중복 여부, 자산 정책을 함께 갱신하라. 불완전한 새 그림으로 교체하지 말라.
6. 각 변경 파일에 대하여 **원본 및 변경본의 width/height, RGBA 여부, 실제 alpha bbox, subjectFillX, 실효 픽셀 밀도, SHA-256, 추정 RGBA 메모리**를 비교하라. `maxDisplayWidth`와 실효 픽셀 비율을 분리해서 확인하고, 최종 화면에서 작은 어종/큰 어종 간 상대 크기를 무너뜨리지 말라. 권고 밀도는 가능하면 1.35배 이상이지만 원본 부재를 픽셀 확대·축소로 속이지 말 것.
7. 사용 가능한 환경에 고해상도 아트 생성 도구가 없다면 **이미지가 개선된 것처럼 새 파일을 꾸미지 말 것**. 대신 원본을 남기고 `docs/hires-art-prompts.md`에 각 대상별 레퍼런스 기반 이미지 생성 프롬프트, 투명 배경/화풍/구도/해상도와 납품 체크리스트를 작성하라. 완료한 코드와 미완료 아트를 별도로 보고하라.

### 구현 / 검사 / 배포
- `python3 -m pip install Pillow`, `npm install` 등 실제 환경에 맞춰 필요한 도구를 설치하고 `npm test`, `npm run audit:fish-assets`, `python3 tools/audit_scene_assets.py`를 실행하라. 필요하면 `npm run test:browser`를 위해 포트 4187에서 로컬 서버를 띄워라.
- CI의 `.github/workflows/v3-validation.yml`이 현재 브랜치명만 대상으로 한다면 새 브랜치에서 동일 검사가 실행되도록 **부작용 없는 별도 CI**를 구성하라. 원본 정규화 잡이 새 브랜치에 예기치 않게 커밋하지 않도록 한다.
- Chromium 모바일 360/390/412px에서 **시작 화면, 수족관, 낚시터 1~4지역, 희귀 포획 화면**을 실제 장면만 보이게 캡처하고 텍스트 겹침, 피사체 잘림, 흐림, 투명 경계, 가로 넘침을 확인하라. 물고기 실제 출현을 검증할 때 테스트용 강제 스폰과 일반 추첨 결과를 혼동하지 말 것.
- 변경을 (A) 고해상도 일반 어종, (B) 지역 배경, (C) 이벤트 아트, (D) QA·문서처럼 **서로 복원 가능한 커밋**으로 나눠라. 가능하면 변경된 파일별 before/after 이미지와 감사 결과를 PR에 기록하라.
- 배포가 필요하다면 기존 GitHub Pages의 `main` 배포를 **변경하지 않고** 새 브랜치의 독립적인 미리보기를 만들 수 있는지 권한·설정을 먼저 확인하라. 가능하지 않으면 로컬 서버 검증·스크린샷 링크를 제공하고 배포했다고 주장하지 말 것.
- 최종 답변은 **실제로 만든 브랜치/커밋/PR 링크, 변경한 PNG 목록, 테스트 결과, 남은 미완료 항목**을 포함하라. 접근 거부/이미지 생성 도구 부재는 명확히 보고하고 기존 작업을 보존하라.

**실행할 수 있는 작업을 우선 끝까지 추진하고, 불필요한 확인 질문 없이 안전한 최선안을 선택하라.**
